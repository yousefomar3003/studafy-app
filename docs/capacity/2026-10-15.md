# Capacity fixes, 15 October 2026

The next item ranked in the [14 October report](2026-10-14.md): the lessons
and conversations lists, built a page at a time. Proven to change no answer,
then measured with the same two harnesses, on top of fixes 1–3 (PR #53).

## The short answer

**The two lists are about four times cheaper, with the same answers.** Their
share of database time falls from about 23% to 9%. On the same machine and
the same synthetic data, before and after:

| | Before | After |
|---|---|---|
| The lessons list, per call (nothing else running) | 12.3 ms | 3.3 ms |
| The conversations list, per call (nothing else running) | 7.2 ms | 1.9 ms |
| Lessons + conversations, share of database time (database-alone mix) | 23.4% | 9.4% |
| Database alone: throughput, 10–200 simultaneous users | 234–354 req/s | 322–399 req/s |
| Database alone: p95 at 10 users | 100 ms | 66–68 ms |
| Through the API at 1,000 people: p50 / p95 | 134 ms / 1.2 s | 38–49 ms / 521–542 ms |
| Through the API at 2,000 people: p50 / p95 | 2.8 s / 4.0 s | 2.0–2.5 s / 3.2–3.6 s |
| Through the API: peak throughput | 320 req/s | 323–349 req/s |

The "after" figures are two runs; see "Measurements" for why.

Every rewritten list was compared against the original, page by page, for
everyone in the pgTAP fixtures and a sample of the scale data, with edge
cases planted: **zero differences**.

## What changed

| Fix | Migration | What it does |
|---|---|---|
| 4. Lessons a page at a time | `202610150001_capacity_lessons_rows_per_page.sql` | Two causes. Finding a class's lessons read every publication in the database, because the only index on publications by class covers published, live ones and the list asks for any (a teacher sees drafts and withdrawn ones too); a plain index on `resource_publications (classroom_id)` now answers it. Then each lesson was built by `api041_resource_json`, one call per row, whose test for the lesson's files (its own file, or one bound to it) no index could answer, so every row read the files table. `api041_resource_rows` builds the page in one query, finding files and links by their indexes. Used by the member list and the guardian's list of a child's lessons |
| 5. Conversations a page at a time | `202610150002_capacity_conversations_rows_per_page.sql` | Each conversation was built by `api042_conversation_json`, which named every participant's role through `messaging_role` → `is_school_staff`: two function calls per participant per conversation, about 160 for a student's three class conversations. `api042_conversation_rows` builds the page in one query, answering the same staff/student/guardian rule for the whole page at once |

No rule changed. In `api041_query_before_notebook`,
`api041_query_pre_roster_shape` and `ops_query_messaging`, only the line that
builds the page changes; the rest of each function is re-stated unchanged, as
`CREATE OR REPLACE` requires. The single-row builders (`api041_resource_json`,
`api042_conversation_json`) stay for single reads and command responses. No
function is renamed or wrapped (ADR-0030).

## Proof: zero differences

The method of 14 October (`scripts/scale/proof/`, see its README): in one
transaction, record every answer, apply the migration, record again, compare,
roll back. On the pgTAP fixtures, which already had the new migrations, the
original functions are restored first in the same transaction, so "before"
runs exactly the code being replaced.

**Lessons** (`differential.sql` with `plant-lessons.sql`): every academic list,
for each person in each school they belong to and on the tenant-less guardian
path, unfiltered, by class and by student, up to three pages each.

| Data | Cases | Pages | Rows compared | Lesson rows | Differences |
|---|---|---|---|---|---|
| Scale, 1 in 1,000 people (102), 1 lesson in 5 planted | 2,922 | 4,536 | 48,889 | 11,933 | **0** |
| pgTAP fixtures, everyone (16), every lesson planted and copied 12 times | 215 | 220 | 402 | 306 | **0** |

The seed has no lesson files, links, drafts or second versions, so
`plant-lessons.sql` adds them: a newer current version with its own file, a
version that is not current, files bound as material (deleted, detached,
bound for results, the version's own file bound again), links (detached, for
results, two at the same position), newer and older publications, drafts,
deleted lessons, a missing current version, and unpublished lessons. The
11,933 scale lesson rows compared included 1,016 with files, 504 with links,
1,068 unpublished, 268 whose current version is missing (a null row) and
2,548 on the guardian path.

**Conversations** (`conversations-differential.sql` with
`plant-conversations.sql`): every sampled person's list with pages of 20, 2
and 1 (so the keyset walks every page and meets ties), and once with a
malformed position.

| Data | People | Cases | Pages | Conversation rows | Participant roles | Differences |
|---|---|---|---|---|---|---|
| Scale, 1 in 100 people, 1 conversation in 5 planted | 1,047 | 4,188 | 6,375 | 6,544 | 169,616 (8,300 staff, 150,220 students, 11,096 guardians) | **0** |
| pgTAP fixtures, everyone (23), conversations made for them | 23 | 92 | 232 | 661 | 2,031 (413 staff, 170 students, 1,448 guardians) | **0** |

The fixtures leave no conversations behind, so the plant first makes one per
school with everyone in it and one between every two people. Then it adds:
guardians and other schools' teachers as participants; teacher memberships
that lapsed, were suspended, ended or have not started; guardians who also
teach, in every membership state; deleted student records; people who left;
read markers; two people with the same name; direct conversations; and equal
activity times.

**The proofs catch mistakes.** Each was run against deliberately broken
versions of the new functions: the staff rule without its end date, the
student rule without the deleted check, links ordered without their creation
time, and the version's own file left out. Each broken version showed
differences (15–56 cases); the real migrations show none.

All 59 pgTAP files pass in CI order on a fresh reset with the two migrations
(including the DB-020 and DB-021 upgrade suites), and so do the query-plan
checks, the database type drift check, and the API and worker integration
suites (405 passed, 0 failed).

## Measurements

**Environment.** As on 14 October: the Supabase local stack (Postgres 17) in
a Docker VM with 10 vCPUs and 8 GB, `scripts/scale/seed-scale.sql` at 100
schools × 500 students, one Bun API process (`DATABASE_POOL_MAX=20`, Redis,
rate limits on), the local AI and sign-in stand-ins, warmed up first.

The machine was shared with other builds and swapping heavily during the
first "before" run, which came out far lower than everything after it. So the
runs were interleaved: before, after, before again (the migrations' functions
replaced by the originals and the index dropped), after again. The tables
compare the repeated "before" with both "after" runs; the first run is in
the footnote. Compare within this report, not with 14 October's absolute
figures.

## Rerunning it

As in the [12 October report](2026-10-12.md#rerunning-it), plus the proofs in
`scripts/scale/proof/README.md`. Building the scale database took 93 minutes
this time instead of 10, because the machine was swapping.

A warning for a machine with several local stacks: `scripts/rehearse-recovery.ts`
(a CI step) finds its container by the label
`com.supabase.cli.project=studafy`, so it reaches the `studafy` stack even
when `DATABASE_URL` names another one. Skip it outside CI.

# Capacity fix 6, 16 October 2026

The next database item ranked in the [15 October report](2026-10-15.md): the
grades list, built a page at a time. Proven to change no answer, then measured
with the same harnesses, on top of fixes 1–5 (PRs #53 and #65).

## The short answer

**The grades list is about two and a half times cheaper per call, with the same
answers.** Its share of database time through the API roughly halves. On the
same machine and the same synthetic data, before and after:

|                                                            | Before          | After            |
| ---------------------------------------------------------- | --------------- | ---------------- |
| A student's grades list, per call (nothing else running)   | 11.2–12.4 ms    | 4.2–5.0 ms       |
| A parent's list of a child's grades, per call              | 10.3–11.4 ms    | 4.1–4.2 ms       |
| A teacher's grades list, per call                          | 14.7–16.3 ms    | 5.6–6.8 ms       |
| The grades lists through the API, mean per call under load | 35.5–37.1 ms    | 16.4–19.5 ms     |
| The grades lists through the API, share of database time   | 12.2–13.3%      | 7.9–8.0%         |
| The per-row builder `api041_grade_json`, calls in a run    | 126,315–128,145 | 0 from the lists |

The end-to-end throughput figures moved within the noise of a shared machine
(see "Measurements"): the grades list was one item among several of similar
size, and the machine was running other agents' stacks throughout.

Every list was compared against the original, page by page, for everyone in the
pgTAP fixtures and a sample of the scale data, with edge cases planted, and the
new page builder was compared against the single-grade builder for every grade
each sampled person could ask about: **zero differences**.

## What changed

| Fix                        | Migration                                        | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| -------------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 6. Grades a page at a time | `202610150040_capacity_grades_rows_per_page.sql` | Each grade was built by `api041_grade_json`, one call per row. Each call asked `coursework_staff` for the grade's class, then found its files and links through `coursework_files_json` and `content_links_json` four times (the grade's own attachments and links, and its assessment's shared results files and links). Those helpers take an either-or filter serving five kinds of owner, so no index answered it, and an assessment's shared results were found again for every grade of it. `api041_grade_rows` builds the page in one query: `coursework_staff` once per class on the page, the grade's files and links by their indexes, an assessment's shared results once per assessment. Used by the member list and the guardian's list of a child's grades |

No rule changed. In `api041_query_before_notebook` and
`api041_query_pre_roster_shape`, only the line that builds the page changes; the
rest of each function is re-stated unchanged, as `CREATE OR REPLACE` requires.
Both re-stated bodies were diffed against the live definitions on the branch's
database: one line differs in each. Those unchanged bodies keep the access calls
they already had (`is_school_admin`, `is_class_staff`, `api041_class_writer`);
the new function uses none of them: who sees a grade's files is still
`coursework_staff`, asked through the same function. `api041_grade_json` stays
for single reads, command responses and the exam attempt view. No function is
renamed or wrapped (ADR-0030). No index was needed: `file_binding_grade_idx`,
`content_links_grade_idx` and the assessment indexes already existed.

## Proof: zero differences

The method of 14 and 15 October (`scripts/scale/proof/`, see its README): in one
transaction, record every answer, apply the migration, record again, compare,
roll back. On the pgTAP fixtures, which already had the migration, the two
original list functions (their definitions before the migration, from
`pg_get_functiondef`) are restored first in the same transaction, so "before"
runs exactly the code being replaced. The scale "before" did the same.

**Lists** (`differential.sql` with `plant-grades.sql`): every academic list, for
each person in each school they belong to and on the tenant-less guardian path,
unfiltered, by class and by student, up to three pages each.

| Data                                                                                   | Cases | Pages | Rows compared | Grade rows | Differences |
| -------------------------------------------------------------------------------------- | ----- | ----- | ------------- | ---------- | ----------- |
| Scale, 1 in 1,000 people (102), 1 grade in 5 and 1 assessment in 3 planted             | 2,952 | 4,714 | 51,033        | 3,928      | **0**       |
| pgTAP fixtures, everyone (16), ten assessments per class added and every grade planted | 221   | 226   | 484           | 223        | **0**       |

**Builders** (`grade-rows-differential.sql`): for every sampled person, every
grade of every class they teach, are enrolled in or have a child in, in any
state (including drafts read by someone who is not the class's teacher), built
by `api041_grade_json` one at a time and by `api041_grade_rows` a class at a
time and one at a time, as that person.

| Data                     | People          | Person-classes | Grades compared | Page differences | Single differences |
| ------------------------ | --------------- | -------------- | --------------- | ---------------- | ------------------ |
| Scale, 1 in 100 people   | 1,047           | 3,083          | 385,375         | **0**            | **0**              |
| pgTAP fixtures, everyone | 10 with classes | 10             | 320             | **0**            | **0**              |

The seed's grades are all published, scored and bare, so `plant-grades.sql`
adds: a grade's own files (one deleted, one detached, one bound for results, one
bound twice, two bound at the same moment) and links (two at the same position
and moment, one detached, one for results); an assessment's shared results files
and links, with material ones that must not show, a deleted file, a detached
binding and link; grades in draft, reviewed and withdrawn, so their files are
hidden from all but the class's teacher; absent, not graded and zero marks, no
mark; feedback; a category weight; a teacher per school with a `school_admin`
membership and an assistant's place in a class (so the list shows them its
drafts, but `coursework_staff` does not); and teachers whose place in a class
has not started (the other way round). The 3,928 scale grade rows compared in
the lists included 207 with files, 197 with links, 452 with shared files, 498
with shared links, 75 not published (27 of them showing files, to their
teacher), 183 absent or not graded, 314 weighted and 607 on the guardian path.
The 385,375 builder comparisons included 30,864 unpublished grades, 92,083 with
files or links, and 531 unpublished ones with files or links shown.

**The proofs catch mistakes.** Both were run against five deliberately broken
versions of the new function: files shown only once published (the teacher's
rule dropped), shared links of any role, a grade's files tie-broken the wrong
way, the raw mark without its "scored" default, and deleted files shown. Every
broken version showed differences:

| ------------------------------ | ------------ | --------------- | ---------------------------- | ------------------ |
| Teacher's rule dropped         | 9 cases      | 4               | 57 grades                    | 22                 |
| Shared links of any role       | 217          | 15              | 4,584                        | 104                |
| Files tie-broken the wrong way | 9            | 4               | 56                           | 18                 |
| Raw mark                       | 323          | 15              | 34,602                       | 210                |
| Deleted files shown            | 115          | 15              | 1,529                        | 80                 |

The real migration shows none.

All pgTAP files pass in CI order on a fresh reset with the migration (including
the DB-020 and DB-021 upgrade suites; two steps that timed out connecting while
the machine was overloaded passed on rerun), and so do the database lint, the
query-plan checks, the database type drift check and the API and worker
integration suites. `scripts/rehearse-recovery.ts` was skipped, as on 15
October: on a machine with several local stacks it finds the `studafy` stack by
label, not the one `DATABASE_URL` names.

(`DATABASE_POOL_MAX=20`, Redis, rate limits on), the local AI and sign-in
stand-ins, a warm-up first. The machine was shared with other agents' stacks
throughout, so the runs were interleaved: before, after, before again (the
original list functions restored), after again. Compare within this report.

## `study_lesson`: not in this PR

`study_lesson` (5.2% here, 14–15 ms a call) picks the newest publication of a
lesson that the caller may see, asking `can_view_resource_publication` of each.
On the scale data every lesson has exactly one publication, so the cost is that
access function itself, not the number of calls. Making it cheaper means
restating its rule (school admin, teacher membership, published and clean file,
audience, enrolment or guardian link) as a set query, with its own proof, and a
new function may not use `is_school_admin` in this release. That is not a small
change, so it is listed next rather than folded in here.

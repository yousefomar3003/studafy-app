# Capacity fixes, 14 October 2026

The first three fixes ranked in the [12 October report](2026-10-12.md), each
proven to change no answer, then measured with the same two harnesses.

## The short answer

**Roughly twice the capacity, with the same answers.** On the same machine
and the same synthetic data, before and after:

| | Before | After |
|---|---|---|
| Database alone: throughput, 10–200 simultaneous users | 132–148 req/s | 294–333 req/s |
| Database alone: p95 at 10 users | 232 ms | 65 ms |
| Through the API: the most people before the database is full | about 500 | about 1,000–1,500 |
| Through the API at 1,000 people: p50 / p95 | 2.6 s / 5.5 s | 89 ms / 762 ms |
| Through the API: peak throughput | 153 req/s | 310 req/s |
| The grades list, per call | 309 ms | 29 ms |
| The homework list, per call | 163 ms | 27 ms |

Every rewritten list was compared against the original, page by page, for
everyone in the pgTAP fixtures and a sample of the scale data, with edge
cases planted: **zero differences**.

## What changed

| Fix | Migration | What it does |
|---|---|---|
| 1. Access rules once per call | `202610140003_capacity_access_sets_once.sql` | The lists asked `is_class_staff` and `can_view_classroom` for every class the caller could see, and `can_view_class_student` for every class/student pair (and per row for a teacher's attendance). The same rules now run once as a few set queries: the classes the caller teaches, the schools they administer, and the class/student pairs where they are the student or a verified guardian |
| 2. Grades from the caller's records | `202610140004_capacity_grades_from_own_records.sql` | The grades list walked the school's grades in id order and filtered each one. It now starts from the grades of the caller's own and linked students and of the classes they teach, by index (`grade_results (student_id, id)`, `assessments (classroom_id)`), then applies exactly the same conditions. An administrator still reads the school |
| 3. Homework rows per page | `202610140005_capacity_homework_rows_per_page.sql` | Each homework row called separate functions for its attachments, links, maximum score, local times and the student's deadline and extension, and the outer list looked up each row's publication date and a child's deadline one by one. `api041_assignment_rows` and `assignment_student_rows` now build a page in one query each |

No rule changed. The single-row reads (`getAssignment`,
`api041_assignment_json`, the access functions themselves) are untouched.

## Proof: zero differences

The scripts are in `scripts/scale/proof/` (see its README). Each proof runs
in one transaction: record every answer, apply the migration, record again,
compare, roll back. The clock does not move inside a transaction, so fields
that depend on the time compare fairly.

**Lists** (`differential.sql`): every academic list, for each person in each
school they belong to and on the tenant-less guardian path, unfiltered, by
class and by student, up to three pages each.

| Fix | Data | Cases | Pages | Rows compared | Differences |
|---|---|---|---|---|---|
| 1 | Scale, 1 in 1,000 people (102: students, parents, teachers) | 2,922 | 4,620 | 49,276 | **0** |
| 1 | pgTAP fixtures, everyone (16) | 215 | 215 | 126 | **0** |
| 2 | Scale sample, on top of fix 1, homework and marks planted | 2,922 | 4,623 | 50,437 | **0** |
| 2 | pgTAP fixtures, on top of fix 1 | 215 | 215 | 126 | **0** |
| 3 | Scale sample, on top of fixes 1–2, homework planted | 2,922 | 4,626 | 50,436 | **0** |
| 3 | pgTAP fixtures, on top of fixes 1–2, homework planted | 215 | 215 | 126 | **0** |

The synthetic seed has no homework links, files, extensions or marked
homework, so `plant-homework.sql` adds them for the proof. The 9,240
homework rows compared for fix 3 included 1,274 with links, 873 with files,
9,000 with a student's deadline, 746 with an extension, 3,955 closed, 369
locked by a published mark, 770 marked through an assessment and 1,826 with
a closing time.

**Access decisions** (`access-differential.sql`, fix 1): the new sets
against the original functions, for every class in every school a person
belongs to and every enrolment they could ask about, after planting the
edge cases the seed lacks (withdrawn, ended and future enrolments, expired
and pending guardian links, lapsed and suspended memberships, archived
classes, closed terms, ended and not-yet-started staff assignments,
suspended profiles, deleted students, a school admin per school):

| Data | People | `is_class_staff` | `can_view_classroom` | `can_view_class_student` | Differences |
|---|---|---|---|---|---|
| Scale, 1 in 100 people plus the planted admins | 1,145 | 68,700 | 68,700 | 8,284 | **0** |
| pgTAP fixtures | 23 | 26 | 26 | 14 | **0** |

All 57 pgTAP files pass in CI order with the three migrations, and so do the
API and worker integration suites.

## Measurements

**Environment.** As on 12 October: the Supabase local stack (Postgres 17) in
a Docker VM with 10 vCPUs and 8 GB, `scripts/scale/seed-scale.sql` at 100
schools × 500 students, one Bun API process (`DATABASE_POOL_MAX=20`, Redis,
rate limits on), the local AI and sign-in stand-ins. Each "before" and
"after" ran on the same machine and data, warmed up first. The absolute
"before" figures are lower than 12 October's on this run; compare within this
report.

### Database alone (`scripts/scale/bench.ts`, full mix)

| Users | Before: req/s, p50 / p95 | After: req/s, p50 / p95 |
|---|---|---|
| 10 | 132, 37 / 232 ms | 333, 24 / 65 ms |
| 50 | 146, 286 / 773 ms | 307, 140 / 332 ms |
| 100 | 137, 689 / 1,725 ms | 324, 270 / 648 ms |
| 200 | 148, 1,419 / 3,210 ms | 294, 650 / 1,286 ms |

p95 per screen at 10 users, before → after: grades 595 → 78 ms, homework
272 → 70 ms, a parent's homework 299 → 113 ms, a parent's grades 138 → 87 ms.

### Through the API (`scripts/scale/http-load.ts`, 4 s pauses)

| People at once | Before: req/s, p50 / p95 | After: req/s, p50 / p95 |
|---|---|---|
| 250 | 63, 45 / 344 ms | 63, 24 / 144 ms |
| 500 | 118, 246 ms / 1.1 s | 128, 23 / 182 ms |
| 1,000 | 153, 2.6 / 5.5 s | 245, 89 / 762 ms |
| 1,500 | 141, 7.9 / 11.4 s | 310, 1.0 / 2.0 s |
| 2,000 | 142, 12.8 / 19.4 s | 290, 3.0 / 6.1 s |

No request failed except one `409 VERSION_CONFLICT` on a notebook save at
1,500 people after the fixes: two simulated saves of the same note, which the
API rightly refuses.

### Where the database time goes now

The grades list is down from 16% of database time (309 ms a call) to 6%
(29 ms); the homework list and its per-row builder from about 26% to 11%;
`can_view_classroom` from 15,032 calls to 3,580. The largest remaining items:

| Share | Statement |
|---|---|
| 8.0% | the lessons list, 36 ms a call: `api041_resource_json` per row (the same per-row pattern fix 3 removed from homework) |
| 6.4% | the grades list, 29 ms a call |
| 6.2% + 5.7% | the conversations list and its per-row builder |
| 6.1% + 5.0% | the homework list and its page builder |

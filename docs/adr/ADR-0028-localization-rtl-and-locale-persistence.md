# ADR-0028: Arabic as a switchable language, RTL, and locale persistence

- Status: Accepted for local/disposable use
- Date: 2026-09-20
- Decision owner: repository owner (GitHub `@yousefomar3003`)
- Decision log: DL-055
- Part of: MOB-070 (bilingual and accessibility acceptance, `instructions.md` §20 Part 7A)

## Context

Studafy declares English and Arabic as its shipped locales, and four slices
were already bilingual. Arabic nevertheless did not work as a language a user
could switch to:

1. **The choice did not survive a restart.** `StudafyLocaleController` was an
   in-memory singleton with no persistence of any kind. Every launch started
   in English.
2. **The device language was never consulted.** `MaterialApp.locale` was
   always set from that singleton, which defaulted to `Locale('en')`, and
   there was no `localeResolutionCallback`. An Arabic phone opened an English
   app.
3. **Neither platform declared Arabic.** `ios/Runner/Info.plist` had no
   `CFBundleLocalizations` and Android had no locale config. iOS therefore
   reported the app as English-only regardless of what Flutter's
   `supportedLocales` said, so device detection could not have worked even
   once it was implemented, and neither OS offered a per-app language setting.
4. **The choice never reached the server.** `profiles.locale` exists,
   `POST /v1/account/profile` accepts it, and the generated Dart client has
   the method — but nothing in `lib/` called it. The worker renders email and
   push copy from the profile locale
   (`apps/worker/src/processors/notificationCopy.ts`), so a user who switched
   the app to Arabic kept receiving English notifications.
5. **About 195 strings on reachable screens were hardcoded English**, and the
   language picker's own chrome was among them: an Arabic reader opening the
   language sheet saw English.
6. **Nothing in `lib/` or `test/` referenced `Directionality`,
   `TextDirection` or `EdgeInsetsDirectional`.** RTL worked only by accident,
   through the ambient direction `GlobalWidgetsLocalizations` sets. Ten
   `EdgeInsets.fromLTRB` call sites and four one-way chevrons did not mirror.

## Decision

### Copy lives in `.arb` files, generated by `flutter gen-l10n`

Replacing the hand-written `Map<String, Map<String, String>>` tables. Two
reasons decided it. A typo in the old lookup rendered the raw key, silently;
generated getters are compile-time checked. And Arabic has six plural
categories, which string interpolation cannot express —
`account_security_page.dart` already read "1 minutes ago" in English and had
no correct Arabic form at all.

One generated class (`AppL10n`), not one per slice: `flutter gen-l10n` only
auto-runs a single `l10n.yaml` configuration, and per-slice classes would have
needed a bespoke script plus one boundary-allowlist entry each. Slice
ownership is kept by key prefix (`securityTitle`, `classesCreate`).

`flutter: generate: true` is set because gen-l10n refuses to run without it.
The generated Dart is still checked into `lib/l10n/generated/`, so the build
never depends on codegen having run and a reviewer can read the diff; CI
regenerates and fails on drift.

### The locale preference is device-scoped, and absence means "follow the device"

Stored through a `DeviceSettingsStore` port backed by `shared_preferences`,
which was already present transitively via `supabase_flutter` and so adds no
native plugin surface.

Deliberately **not** `SecureStore`: that port documents itself as session
material and its `deleteAll()` runs on sign-out and account switch. A language
choice should outlive sign-out — a shared school tablet must stay in the
language the last person chose. The `SecureStore` comment forbidding "shared
preferences" is about session material, not about the package.

A stored preference is a *choice*; its absence means follow the device, not
"English". That is what makes first launch on an Arabic phone open in Arabic.

### The controller is the single authority for the rendered language

`LocaleController` is constructed by the composition root, restored in
`AppBootstrap.initialize` before the first frame (so the app never paints
English and flips), and exposed through a `LocaleScope` `InheritedNotifier` in
`core/` — `core` rather than `app` because feature presentation opens the
language picker and features may not import composition-root wiring.

`MaterialApp.locale` is set from `controller.resolvedLocale`, never left null.
An earlier draft let Flutter resolve the device locale independently; that
created two sources of truth, and the language rendered could have drifted
from the language published to the server. The controller observes the widgets
binding instead, so a system language change still reaches the app.

### The device's own choice outranks the profile

The profile locale seeds a device that has never been told what to use — so
signing in on a new phone keeps your language — but never overrides a choice
made on this device. Otherwise switching language on one phone would silently
flip another mid-session.

Publishing is best-effort: the interface changes immediately, and a failed
publish is retried on the next launch by comparing against a second stored
key. Synthetic builds have no profile and skip it entirely.

### User content is never translated, and keeps its own direction

Messages, names, class and assignment titles, school names and notes render
verbatim. This is held by three mechanisms rather than by habit:

- **Structural.** Copy exists only in `.arb` files; user content arrives only
  as a domain field. There is no path from one to the other.
- **Enforced.** `mob070_rtl_source_test.dart` fails if a copy lookup is handed
  a runtime value rather than a key written in the source.
- **Directional.** `UserContentText` infers direction from the string itself,
  using `intl`'s `Bidi.detectRtlDirectionality` — the Unicode UAX#9
  first-strong-character rule — and falls back to the ambient direction for
  text with no strong character (a bare number, an ID like `STU-42`). Without
  it, an Arabic message inside an English screen lays out left-to-right and
  its punctuation lands on the wrong end.

### Arabic interface, Western digits

Grades, counts and dates render 0-9 in both languages, with Arabic month and
day names. `intl`'s Arabic data uses Eastern Arabic-Indic numerals by default
— verified, not assumed: a date formatted under `ar` in the Flutter runtime
came out as `١٧ سبتمبر ٢٠٢٦` — so `core/studafy_formatting.dart` applies an
explicit override.

Three reasons: identifiers like `STU-42` appear inside body copy and must stay
readable and copy-pasteable; grades must match the ASCII copy the server sends
by email and push; and Gulf school software overwhelmingly uses Western
digits. This is a **product judgement, not a technical constraint**, so it is
confined to one function and recorded as revisitable.

### Scope: screens a real school user can reach

Translated: session, account, academic, classes, teacher dashboard,
notifications, messaging, family, the app shell, the language picker, the
synthetic banner and the containment page.

**Not translated: `lib/legacy/teacher`, `lib/legacy/student` and the
synthetic-path `lib/features/parent/presentation` screens** — about 180
strings. They are unreachable when `RuntimePolicy.requiresRemoteBackend`
(`parent_shell.dart`, `teacher_shell.dart`), every such screen renders under a
`SYNTHETIC DATA — NOT FOR REAL SCHOOL USE` banner, and MOB-070's acceptance
criteria require those modules to be removed. Translating them would spend the
scarcest resource here — a human Arabic reviewer — on copy with a scheduled
deletion date. Recorded as **bounded**, with MOB-070 as the trigger.

## Consequences

Arabic is a language a user can switch to, that survives restart, that the
phone's own setting selects on first launch, and that reaches the profile so
server-sent email and push match.

Open, and gated behind a physical device — CI cannot cover any of it, and a
green test run must not be read as covering it:

1. **Arabic text shaping and font fallback** — ligatures, diacritics and
   kashida differ between iOS and Android system fonts. `flutter test` renders
   with a test font, so no automated test here proves Arabic *renders*.
2. **Line height and clipping.** Arabic runs taller and roughly 20-25% longer
   than English. Fixed heights — the synthetic banner's `SizedBox(height: 30)`,
   chip labels, `ListTile` densities — may clip before any test notices.
3. **VoiceOver and TalkBack in Arabic**, including reading order in an RTL
   tree and how a `UserContentText` string inside the opposite-direction
   interface is announced. Required for MOB-070 sign-off.
4. **Font scale at 200% in Arabic.**
5. **First-launch detection on real device configurations** — `ar-SA`,
   `ar-EG`, `ar` with an English region, and the iOS per-app language
   override.
6. **The push and email loop.** Tests prove copy *selection*, not delivery,
   which additionally needs Firebase and a verified sending domain that do not
   exist yet (DL-053).

**The Arabic copy in this change has not been reviewed by a native speaker.**
It is fit for development and review, not for launch. School vocabulary
especially — assignment, attendance, guardian, term — has conventional Arabic
that a grammatically correct translation can still get wrong for schools. The
placeholder privacy and terms bodies in `login_page.dart` additionally carry
legal text that counsel has not reviewed in either language; REL-002 §21.6
replaces both with hosted documents.

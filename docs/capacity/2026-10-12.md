# Capacity re-measure, 12 October 2026

Launch plan 4.8. This measures how many people Studafy serves at once now that
it has online exams, study notebooks and AI study tools. It replaces the
headline numbers in `docs/operations/capacity.md` (2026-09-29).

## The short answer

On a 10-vCPU database, with 100 schools, 50,000 students, 50,000 parents and
4,000 teachers (about 11 million rows), and the real API in front of it:

| | Through the API (what people feel) | Database alone |
|---|---|---|
| Comfortable (95% of requests under 400 ms) | **~130 requests/s** | ~260 requests/s |
| Saturated (the database at 100% CPU) | ~200–230 requests/s, with waits of 3–6 s | ~300–330 requests/s |
| Errors at 4× the comfortable load | **none**: requests slow down, they do not fail | none |

In people, the app makes about one request every 10 seconds per person using
it:

- **Comfortable: about 1,300 people using the app at the same moment** per
  10-vCPU database. With 10–20% of a day's users active at the busiest moment,
  that is roughly **6,500–13,000 daily active users**.
- Beyond about 2,000 at once, pages take several seconds.

**The first bottleneck is database CPU.** The API process (under half of one
core at saturation), Redis (under 1% CPU) and the AI provider are far from
their limits when the database is full.

**This is about a third of the 2026-09-29 estimate** (4,400 people at once).
Two reasons:

- That figure was the database alone. Every request through the API adds
  its own database work (identity, idempotency, rate limits): about 30% less
  throughput.
- The same screens are about 40% more expensive in the database than on
  2026-09-29 (300 instead of ~500 requests/s with the old screen mix). Hot
  per-row builders were rewritten since, for paper marks, deadlines,
  editable lessons and online exams (see "First bottleneck").

## Method

**Environment.** Everything ran locally, on a throwaway copy, with synthetic
data only. Nothing hosted was touched and no paid AI call was made.

| | |
|---|---|
| Database | Supabase local stack (Postgres 17), Docker VM with 10 vCPUs and 8 GB, the same as 2026-09-29. Default `shared_buffers` (128 MB); `pg_stat_statements.track = all` |
| Data | `scripts/scale/seed-scale.sql`: 100 schools × 500 students, a parent each, 40 teachers, 60 classes; lessons, homework, 2.25 M hand-ins, 750 k grades, 3 M attendance marks, 1 M notifications, messages. **New:** 2 online exams per class (5 questions each), a ready study notebook per student, 30% of students on Max and 20% on Plus |
| API | One Bun process (`apps/api`), as deployed: rate limits on, Redis caches on, `DATABASE_POOL_MAX=20`, JSON validation, logging at `warn` |
| AI provider | A local stand-in speaking the provider's API over HTTPS, answering in 2.5 s ± a third (the real Qwen3.5-9B answers a question in about 2 s) |
| Sign-in | A local signing-key server; the runner signs a token for each synthetic person, which the API verifies exactly as it verifies Supabase's |

**Two harnesses.**

1. **Database alone** (`scripts/scale/bench.ts`). Replays each request's
   authorization and query against the database, flat out, at 10–200
   simultaneous users. `--classic` runs only the screens measured on
   2026-09-29.
2. **Through the API** (`scripts/scale/http-load.ts`, new). 250–2,000
   simultaneous people, each pausing about 4 s (exponential) between
   screens. Each person gets their own IP address, as phones do.

**The mix.** Students 70%, parents 20%, teachers 10%.

- **Every student visit:** classes, homework, lessons, grades, unread count.
- **Then one of these:**
  - **exams (40%):** the list, an exam's questions; 30% of these also hand it in;
  - **notebooks (40%):** the class's notebooks, open one; half also save a note;
  - **AI (20%):** the usage bar; paid students also ask a question (database
    run: the allowance hold and settle, or the quiz-cache lookup and store).
- **Teachers:** classes, roster, attendance, hand-ins, exam attempts, and
  sometimes a message.
- **Parents:** their children, a child's homework and grades, unread count.

The new screens are no heavier than the old ones on average. At 10 users the
p95s were:

- **Cheaper than average:**
  - notebook open 37 ms, notebook save 42 ms, the class's notebooks 35 ms;
  - exam questions 31 ms, exam hand-in 54 ms, teacher's exam attempts 25 ms;
  - the AI allowance hold 19 ms and settle 24 ms;
  - the quiz-cache lookup 66 ms.
- **The expensive screens are old ones:** grades 228 ms and homework 130 ms.

## First bottleneck: database CPU

The database reaches 100% CPU at about 200 requests/s through the API and
300 requests/s alone. Here is where its time went (`pg_stat_statements`, all
runs):

| Share | Statement | What it is |
|---|---|---|
| 14.1% | the grades list (117 ms a call) | `listGradeResults`: scans the school's grades, then checks each |
| 9.1% + 8.9% | the homework list and its per-row builder (72 ms a list; 2.8 ms per row) | `api041_assignment_json` makes six lookups for every row: attachments, links, maximum score, two local-time conversions, and the student's deadline and extension |
| 8.4% + 7.9% + 6.0% + 5.8% | access checks | `is_class_staff`/`can_view_classroom` per class, the caller's class/student pairs, and `enrollments` existence checks, recomputed for every list and row |
| 6.7% | the student's own deadline and extension per homework row | `assignment_student_json` |
| 3.0% each | lessons list, conversations list | |

Together, the access checks are **about 28%** of database time. The grades
and homework lists, with their row builders, are **about 39%**.

## AI: latency and cost, modelled separately

| Feature | Latency (real provider, measured 2026-10-08) | Tokens per use (typical) | Cost per use at $0.17 / $0.25 per M tokens |
|---|---|---|---|
| Ask the helper | ~2 s | 1.5 k–6 k in (with chosen material), ~350 out | $0.0003–0.0011 |
| Quiz | 6–9 s | ~6 k in, ~1.4 k out | ~$0.0014, **once per lesson version**: later classmates get the stored copy |
| Flashcards | 4–5 s | ~6 k in, ~1 k out | ~$0.0013, stored the same way |
| Study notebook | 8–14 s | ~8 k in, ~2.5 k out | ~$0.002 per generation |

- **Spend has a hard cap.** `private.api047_ai_usage` refuses work past the
  plan's allowance: 40 k tokens a week free, 3 M a month on Plus, 6 M on Max,
  and dollar caps of $0.80 (Plus) and $1.60 (Max) per student per month.
  - A free student costs at most about $0.008 a week.
  - A Max student using every token costs about $1.09 a month, inside the cap
    and well under the $5.99 price.
- **AI is not the capacity limit.**
  - At 1,000 people the run made about 1.8 AI questions a second (108 in a
    minute), with at most 17 waiting on the provider at once; 35 at 2,000.
  - The API holds no database connection while it waits, so this load is
    on the provider's side.
  - Check the provider account's request rate limit covers the peak (about
    110 a minute per 1,000 people at once, plus notebooks and quizzes).
- **Notebooks are written inside the API process**, as a background promise
  (handoff, section 6). Many at once compete with requests for the same
  process. Fix 4 below.

## What it means for production

Scale by database vCPUs: about 13 comfortable requests/s per vCPU through
the API here. The VM runs on Apple silicon, so confirm on the real plan
(fix 6).

| Database vCPUs | Comfortable requests/s | People at once | Daily active users (est.) |
|---|---|---|---|
| 2 | ~25 | ~250 | ~1,300–2,500 |
| 4 | ~50 | ~500 | ~2,500–5,000 |
| 8 | ~100 | ~1,000 | ~5,000–10,000 |
| 10 | ~130 | ~1,300 | ~6,500–13,000 |

**Recommendation for launch:**

- **Database size:** a database with **at least 4 dedicated vCPUs**, which
  covers a pilot of a few schools with room to spare. Move up before about
  half the comfortable figure is reached at the busiest hour.
- **Pool settings:**
  - Keep `DATABASE_POOL_MAX` at 10 per API process (`fly.api.toml`) and per
    worker, through Supabase's session pooler.
  - Keep (API processes × 10) + 10 under the plan's connection limit.
  - One API process used under half a core at the database's limit, so two
    API machines (for availability) are plenty until the database is several
    times larger.

## Fixes, ranked by impact

1. **Access checks once per request, not per row** (about 28% of database
   time). Work out the caller's visible classes and student records once per
   transaction, for example in a transaction-local temporary table or
   setting. Then test row membership against that set instead of calling
   `is_class_staff`/`can_view_classroom` again and again. Each list gets
   cheaper. Prove it with the same zero-difference comparison used on
   2026-09-29.
2. **The grades list from the caller's own records** (14%; the slowest
   screen). Start from the caller's students or classes and page with a
   keyset per class, as 2026-09-29's "next improvement" said. Today it scans
   the school's grades and filters.
3. **Homework rows built for the whole page at once** (about 25% with the
   student's deadline JSON). Attachments, links, maximum score, local times
   and the student's deadline are fetched per row by separate functions.
   Gather them for the page's 20 ids in one set-based query each.
4. **Notebook writing on the worker queue** (moved from the API process).
   It is not the bottleneck today, but many notebooks at once would compete
   with requests in the same process. On the worker it also survives restarts
   (handoff, section 6).
5. **A larger `shared_buffers` and `work_mem`** on the production database,
   sized by the plan. The test used Postgres defaults; this is a config change
   to check on the real plan.
6. **Run `http-load.ts` against a staging Supabase project of the chosen
   size before launch**, to replace the per-vCPU estimate with a measurement.

## Rerunning it

```sh
# 1. The scale database, on a throwaway stack (here the one on port 55722):
SOURCE_DATABASE_URL=postgresql://supabase_admin:postgres@127.0.0.1:55722/postgres \
ADMIN_URL=postgresql://supabase_admin:postgres@127.0.0.1:55722/postgres \
bash scripts/scale/prepare-scale-db.sh          # about 10 minutes

# 2. Database alone (add --classic for the 2026-09-29 screens only):
SCALE_DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:55722/studafy_scale \
bun scripts/scale/bench.ts --pool 20 --users 10,50,100,200 --seconds 20

# 3. Through the API. A self-signed certificate for the AI stand-in:
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:prime256v1 -nodes -days 2 \
  -subj "/CN=127.0.0.1" -addext "subjectAltName=IP:127.0.0.1" -keyout ai.key -out ai.pem
bun scripts/scale/http-load.ts --cert ai.pem --key ai.key \
  --users 250,500,1000,1500,2000 --seconds 60 --think 4000
#    then, from a directory without the repository's .env, start the API with
#    what the runner prints, plus DATABASE_URL (the scale database),
#    REDIS_URL (a spare Redis database), API_PORT=8899, ENVIRONMENT=development,
#    CLIENT_IP_SOURCE=forwarded and random API_CURSOR_SIGNING_KEY,
#    CLASS_JOIN_CODE_KEY and RATE_LIMIT_HMAC_SIGNING_KEY values.

# 4. Where the database time went:
psql postgresql://supabase_admin:postgres@127.0.0.1:55722/studafy_scale \
  -f scripts/scale/top-statements.sql
```

**Harness fixes made for this run:**

- **The seed failed** on `profiles.public_id`, which has been mandatory since
  2026-10-01. It now mints one per person.
- **Ids were not valid UUIDs for the API.** They are now version-4 shaped,
  because the API validates ids strictly.
- **The database bench sent `limit`**, which the SQL ignores, so lists
  returned 50 rows instead of 20. It now sends `pageSize`.
- **Academic writes** now go through `api041_command`.
- **Study routes** run with no authorization call and no school, as the API
  does.
